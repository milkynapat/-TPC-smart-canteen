PROJECT GUIDE · UX/UI + REAL SYSTEM

Smart Canteen
Queue & Pre-order System

คู่มือพัฒนาโปรเจกต์ระบบสั่งอาหารล่วงหน้า จัดการคิว และกระจายเวลารับอาหาร สำหรับโรงอาหารท่าพระจันทร์ ครอบคลุม User Research, UX Flow, MVP, เทคโนโลยี และการประเมินผล

วิธีใช้เอกสารนี้

เอกสารนี้เป็นกรอบเริ่มต้นสำหรับพัฒนาโปรเจกต์ ไม่ใช่ผลการวิจัยที่เก็บจากโรงอาหารแล้ว ประเด็นปัญหาทั้งหมดควรตรวจสอบกับนักศึกษา ร้านค้า และผู้ดูแลพื้นที่ก่อนสรุปเป็นข้อเท็จจริง

จัดทำเป็นแนวทางเบื้องต้น · ชื่อโครงการเป็นชื่อชั่วคราว · ตรวจสอบแหล่งข้อมูลก่อนอ้างอิงในรายงานฉบับส่ง

1. ภาพรวมโครงการ

ชื่อโครงการ (ชื่อชั่วคราว): Smart Canteen Queue & Pre-order System

แนวคิด: ระบบสั่งอาหารล่วงหน้า เลือกเวลารับอาหาร และติดตามสถานะออเดอร์ โดยมีหน้าจัดการออเดอร์สำหรับพ่อค้าแม่ค้า และระบบกลางช่วยจำกัดจำนวนออเดอร์ตามกำลังการผลิตของแต่ละร้าน

เป้าหมายหลัก

  • ลดเวลาที่นักศึกษาต้องใช้ในการสั่งและรออาหาร
  • ลดการกระจุกตัวหน้าเคาน์เตอร์ด้วยการกระจายเวลารับอาหาร
  • ช่วยร้านจัดลำดับออเดอร์และรับงานตามกำลังที่ทำได้จริง
  • ทดลองวัดผลก่อนขยายไปยังร้านอื่นหรือทั้งโรงอาหาร

สิ่งที่โครงการนี้ไม่ใช่

ไม่ใช่แค่แอปแสดงเมนูหรือรับออเดอร์ แต่เป็นระบบประสานเวลาและกำลังการผลิตระหว่างนักศึกษา ร้านค้า และระบบกลาง ทั้งนี้ การสั่งล่วงหน้าไม่สามารถเพิ่มจำนวนที่นั่งหรือทำให้อาหารสุกเร็วขึ้นได้โดยตรง

2. ปัญหาและสมมติฐาน

ปัญหาต่อไปนี้เป็นสมมติฐานตั้งต้นที่ต้องตรวจสอบกับผู้ใช้จริง ยังไม่ใช่ข้อสรุปว่าทุกคนในโรงอาหารท่าพระจันทร์พบปัญหาเหล่านี้

ปัญหาที่คาดว่าจะพบ

  • นักศึกษามีเวลาพักจำกัดและไม่ทราบเวลารอที่แท้จริง
  • คนจำนวนมากอาจลงมาซื้ออาหารในช่วงเวลาใกล้เคียงกัน
  • ร้านต้องรับออเดอร์ ทำอาหาร รับเงิน และส่งมอบอาหารพร้อมกัน
  • นักศึกษาอาจเดินกลับไปถามสถานะอาหารหลายครั้ง
  • การรับออเดอร์ออนไลน์โดยไม่จำกัดจำนวนอาจทำให้ร้านทำไม่ทัน

สมมติฐานสาเหตุ

  • Demand concentration: ความต้องการซื้ออาหารกระจุกตัวในช่วงเวลาเดียวกัน
  • Lack of visibility: ลูกค้าไม่เห็นสถานะคิวหรือเวลารอที่เชื่อถือได้
  • Limited kitchen capacity: กำลังการผลิตของแต่ละร้านมีข้อจำกัด
  • Uncoordinated pickup: เวลาอาหารเสร็จและเวลาที่ลูกค้ามารับไม่ตรงกัน

ขอบเขตของปัญหา

ระบบมุ่งแก้การรอคิว การจัดการออเดอร์ และการกระจายเวลารับอาหารเป็นหลัก ส่วนปัญหาที่นั่งไม่พอหรือทางเดินแคบเป็นข้อจำกัดทางกายภาพที่อาจต้องใช้มาตรการอื่นร่วมด้วย

3. Problem Statement และวัตถุประสงค์

นักศึกษาที่ใช้โรงอาหารท่าพระจันทร์มีเวลาจำกัดในการรับประทานอาหาร ขณะที่ความต้องการซื้ออาหารอาจกระจุกตัวในช่วงเวลาเดียวกัน ทำให้เกิดการรอคอยและความแออัด ส่วนผู้ประกอบการต้องจัดการออเดอร์จำนวนมากด้วยทรัพยากรที่มีจำกัด จึงจำเป็นต้องมีระบบที่ช่วยประสานการสั่งอาหาร เวลาทำอาหาร และเวลารับอาหารให้เหมาะสมกับกำลังการผลิตของแต่ละร้าน

วัตถุประสงค์

  • ออกแบบและพัฒนาระบบสั่งอาหารล่วงหน้าและจัดการคิวสำหรับโรงอาหารท่าพระจันทร์
  • ช่วยให้นักศึกษาวางแผนเวลารับอาหารและติดตามสถานะได้
  • ช่วยให้ร้านจัดลำดับออเดอร์และจำกัดจำนวนงานตามกำลังการผลิต
  • ประเมินผลด้านเวลารอ ความตรงต่อเวลา ความแออัด และความง่ายในการใช้งาน

คำถามวิจัย

  1. นักศึกษาต้องการสั่งอาหารล่วงหน้าและยอมมารับตามช่วงเวลาที่กำหนดหรือไม่?
  2. ร้านค้าสามารถจัดการออเดอร์ล่วงหน้าควบคู่กับลูกค้าหน้าร้านได้หรือไม่?
  3. การแบ่งรอบเวลารับช่วยลดการกระจุกตัวบริเวณจุดรับอาหารได้มากน้อยเพียงใด?

4. กลุ่มผู้ใช้และ User Research

กลุ่มผู้ใช้หลัก

  • นักศึกษา: เลือกเมนู สั่งอาหาร เลือกเวลารับ ติดตามสถานะ และรับอาหาร
  • พ่อค้าแม่ค้า: จัดการเมนู เปิด–ปิดรับออเดอร์ รับงาน เปลี่ยนสถานะ และส่งมอบอาหาร
  • ผู้ดูแลระบบ: จัดการร้านค้า ตรวจสอบปัญหา และดูข้อมูลการใช้งานที่จำเป็น

จำนวนผู้เข้าร่วมที่แนะนำสำหรับการสำรวจตั้งต้น

นักศึกษา 12–15 คน, ร้านค้า 5–8 ร้าน และผู้ดูแลโรงอาหาร 1–2 คนหากเข้าถึงได้ ตัวเลขนี้เป็นจุดเริ่มต้นสำหรับโครงการนักศึกษา ไม่ได้ยืนยันว่าเป็นตัวแทนของผู้ใช้ทั้งหมด หากต้องการสรุปเชิงปริมาณควรเพิ่มการสำรวจ

คำถามสัมภาษณ์นักศึกษา

  1. ปกติซื้ออาหารช่วงเวลาไหน และใช้เวลาทั้งหมดกี่นาที?
  2. เล่าครั้งล่าสุดที่ต้องรออาหารนานให้ฟัง
  3. เสียเวลามากที่สุดตอนรอสั่ง รออาหาร หรือหาที่นั่ง?
  4. เคยอยากสั่งอาหารไว้ก่อนเลิกเรียนไหม เพราะอะไร?
  5. ถ้าเลือกเวลารับได้ อยากเลือกแบบใดและเพราะอะไร?
  6. ถ้าอาหารล่าช้ากว่าเวลาที่แจ้ง จะทำอย่างไร?
  7. อะไรจะทำให้ไม่อยากใช้ระบบสั่งล่วงหน้า?

คำถามสัมภาษณ์ร้านค้า

  1. ช่วงเวลาไหนลูกค้าเยอะที่สุด และร้านรับออเดอร์พร้อมกันได้เท่าไร?
  2. เมนูไหนทำเร็วหรือช้าที่สุด?
  3. ถ้ามีออเดอร์ล่วงหน้า จะจัดลำดับกับลูกค้าหน้าร้านอย่างไร?
  4. ร้านมีมือถือ แท็บเล็ต หรือ POS ที่ใช้อยู่แล้วหรือไม่?
  5. การกดเปลี่ยนสถานะบนมือถือจะช่วยหรือลดความคล่องตัว?
  6. อะไรจะทำให้ร้านไม่อยากใช้ระบบ?
  7. ร้านอยากให้ระบบช่วยเรื่องใดมากที่สุด?

การสังเกตพื้นที่จริง

  • นับจำนวนคนรอหน้าแต่ละร้านเป็นช่วงเวลา
  • จับเวลาตั้งแต่เข้าคิวจนสั่งเสร็จ และตั้งแต่สั่งจนได้รับอาหาร
  • สังเกตการยืนรอและจุดที่คนกระจุกตัว
  • บันทึกจำนวนที่นั่งว่างโดยประมาณ
  • เปรียบเทียบร้านที่มีคิวมากแต่ทำอาหารเร็วหรือช้า

ควรสังเกตอย่างน้อย 3 ช่วง ได้แก่ ก่อนเที่ยง ช่วงเที่ยง และหลังช่วงเร่งด่วน โดยขออนุญาตก่อนสัมภาษณ์หรือเก็บข้อมูลที่อาจระบุตัวบุคคล

5. คู่แข่งและระบบใกล้เคียง

มีผลิตภัณฑ์และกรณีศึกษาที่มีฟังก์ชันใกล้เคียงอยู่แล้ว จึงควรใช้เป็นแหล่งเรียนรู้ ไม่ควรกล่าวอ้างว่าแนวคิดนี้เป็นระบบแรกหรือไม่มีคู่แข่ง

ตัวอย่างสำหรับศึกษา

  • Toast Online Ordering: ระบบเชิงพาณิชย์สำหรับสั่งอาหารและจัดการออเดอร์ — https://pos.toasttab.com/products/online-ordering/
  • Naham University Cafeteria App: กรณีศึกษา UX/UI เกี่ยวกับการสั่งอาหารในมหาวิทยาลัย — https://natheer.framer.website/nahamapp
  • TACTECH Cafe Order: กรณีศึกษาการจัดเวลารับและความสามารถในการผลิต — https://tactech.tech/work/cafe-order
  • QueueUp: โปรเจกต์ระบบโรงอาหารที่เผยแพร่โค้ด — https://github.com/easy-web-p/Queue-up

จุดที่ควรนำมาศึกษา

  • หน้าร้านค้าที่เห็นออเดอร์ทั้งหมดและเปลี่ยนสถานะได้ง่าย
  • การแสดงสถานะและเวลารับที่ชัดเจน
  • การจำกัดจำนวนออเดอร์ต่อช่วงเวลา
  • การแบ่งกำลังการผลิตระหว่างลูกค้าหน้าร้านและออนไลน์
  • การจัดการกรณีออเดอร์ล่าช้าหรือไม่มีผู้มารับ

ตำแหน่งผลิตภัณฑ์ที่เสนอ

ระบบจัดคิวและเวลารับอาหารที่ออกแบบให้เหมาะกับร้านอาหารขนาดเล็กในโรงอาหารมหาวิทยาลัย โดยไม่จำเป็นต้องซื้อเครื่องเรียกคิวราคาแพงตั้งแต่เริ่มต้น

ต้องตรวจสอบฟังก์ชันและสถานะปัจจุบันของแต่ละผลิตภัณฑ์จากเว็บไซต์ต้นทางอีกครั้งก่อนนำไปอ้างอิงในรายงานฉบับส่ง

6. User Flow ฝั่งนักศึกษา

  1. เปิดเว็บแอปและเข้าสู่ระบบตามรูปแบบที่กำหนด
  2. เลือกโรงอาหารหรือร้านค้าและดูเมนู ราคา และสถานะเปิดรับ
  3. เลือกอาหาร จำนวน และรายละเอียด
  4. เลือกรอบเวลารับที่ยังมีความจุเหลือ
  5. ตรวจสอบยอดรวมและยืนยันออเดอร์
  6. ได้รับหมายเลขออเดอร์และเวลารับ
  7. ติดตามสถานะ: รับออเดอร์แล้ว → กำลังทำ → พร้อมรับ
  8. เดินไปรับอาหารและแสดงหมายเลขหรือ QR Code
  9. ยืนยันการรับและแจ้งปัญหาได้หากจำเป็น

กรณีที่ต้องออกแบบเพิ่ม

  • หากรอบที่ต้องการเต็ม ให้แนะนำรอบถัดไป
  • หากร้านยังไม่ยืนยัน ให้แสดงสถานะรอการยืนยัน ไม่รับประกันเวลาเกินจริง
  • หากร้านแจ้งล่าช้า ให้แสดงเวลาใหม่และตัวเลือกตามนโยบายยกเลิก
  • หากอินเทอร์เน็ตขัดข้อง ให้ผู้ใช้ยังตรวจสอบหมายเลขออเดอร์ได้จากหน้ารายละเอียดเมื่อเชื่อมต่อกลับ

7. User Flow ฝั่งร้านค้า

  1. เข้าสู่หน้าร้านค้า
  2. ตั้งค่าเวลาทำการ เมนู ราคา และเวลาทำโดยประมาณ
  3. กำหนดจำนวนออเดอร์ที่รับได้ในแต่ละช่วงเวลา
  4. รับการแจ้งเตือนออเดอร์ใหม่
  5. ตรวจสอบรายการและยืนยันหรือปฏิเสธตามกติกา
  6. เริ่มทำอาหารและเปลี่ยนสถานะ
  7. กดพร้อมรับเมื่ออาหารเสร็จ
  8. ตรวจสอบหมายเลขออเดอร์และส่งมอบ
  9. ยืนยันการส่งมอบหรือแจ้งปัญหา

สถานะออเดอร์ที่แนะนำ

  • รอร้านยืนยัน
  • ยืนยันแล้ว
  • กำลังเตรียม
  • พร้อมรับ
  • รับแล้ว
  • ยกเลิก
  • ล่าช้า / ต้องตรวจสอบ

ควรจำกัดจำนวนปุ่มและข้อความให้ชัดเจน เพราะผู้ขายต้องใช้งานขณะทำอาหารและรับลูกค้าหน้าร้าน ไม่ควรให้ต้องกรอกข้อมูลยาว ๆ ทุกครั้ง

8. ฟีเจอร์หลักและการจัดลำดับ

MVP — ต้องมีในเวอร์ชันแรก

  • รายการร้านค้าและเมนูที่เปิดขาย
  • เลือกเมนู จำนวน และรายละเอียด
  • เลือกรอบเวลารับที่ยังไม่เต็ม
  • สร้างหมายเลขออเดอร์และบันทึกข้อมูล
  • หน้าจัดการออเดอร์สำหรับร้านค้า
  • เปลี่ยนสถานะและแสดงสถานะล่าสุดให้ทั้งสองฝั่ง
  • หยุดรับออเดอร์ชั่วคราว
  • ยืนยันการส่งมอบอาหาร
  • บันทึกเวลาและเหตุการณ์สำคัญเพื่อประเมินผล

ระยะต่อไป

  • วิเคราะห์ช่วงเวลาที่มีออเดอร์สูง
  • แสดงความหนาแน่นจากข้อมูลที่เชื่อถือได้
  • แสดงที่นั่งว่าง หากมีวิธีเก็บข้อมูลที่เหมาะสม
  • เชื่อมต่อระบบชำระเงินออนไลน์
  • QR Code สำหรับรับอาหาร
  • ระบบรีวิว โปรโมชัน หรือสะสมแต้ม

ยังไม่แนะนำสำหรับ MVP

  • AI ทำนายเวลารอแบบซับซ้อน
  • แอปแยก iOS และ Android
  • ระบบส่งอาหารถึงโต๊ะ
  • ระบบจองที่นั่ง
  • การเชื่อมต่อเครื่องเรียกคิวฮาร์ดแวร์
  • ระบบสะสมแต้มและการตลาด

แนวทางเริ่มต้นที่เหมาะสมคือ Responsive Web App หรือ PWA เพื่อให้เปิดผ่านเบราว์เซอร์บนมือถือได้ โดยไม่ต้องติดตั้งแอปแยกตั้งแต่แรก

9. หลักการจัดคิวและเวลารับ

การเลือกเวลาอย่างเดียวไม่พอ ระบบต้องจองความจุของช่วงเวลาในฐานข้อมูลและป้องกันการรับออเดอร์เกินกำลัง

กติกาพื้นฐาน

  1. ร้านกำหนดเวลาทำโดยประมาณและความจุในแต่ละช่วง
  2. กันกำลังการผลิตส่วนหนึ่งสำหรับลูกค้าหน้าร้าน
  3. ระบบแสดงเฉพาะรอบที่ยังมีความจุเหลือ
  4. เมื่อผู้ใช้ยืนยัน ระบบต้องจองความจุทันที
  5. หากเต็ม ให้เสนอรอบถัดไปแทน
  6. ร้านสามารถหยุดรับออเดอร์ชั่วคราวได้
  7. เมื่อเกิดความล่าช้า ร้านแจ้งเวลาใหม่และระบบส่งสถานะให้ลูกค้า

ตัวอย่างเพื่ออธิบายหลักการ

สมมติร้านทำได้ 6 ออเดอร์ใน 10 นาที และกันกำลังผลิตสำหรับลูกค้าหน้าร้านไว้บางส่วน ระบบอาจเปิดรับออนไลน์ 4 ออเดอร์ในช่วงนั้น ตัวเลขนี้เป็นเพียงตัวอย่าง ต้องวัดความสามารถของร้านจริงก่อนกำหนดค่า

กรณีจองพร้อมกัน

หากเหลือ 1 คิวและมีผู้ใช้สองคนกดยืนยันพร้อมกัน ระบบหลังบ้านต้องรับเพียงหนึ่งออเดอร์ อีกคนต้องได้รับข้อความว่ารอบเต็มและเลือกเวลาใหม่ได้ ห้ามอาศัยเพียงตัวเลขที่แสดงบนหน้าจอ

การชำระเงิน

  • เริ่มต้นด้วยการสั่งล่วงหน้าและชำระที่ร้านได้ เพื่อลดความซับซ้อนของ MVP
  • ต้องมีเงื่อนไขยกเลิกและออเดอร์ที่ไม่มารับ
  • เพิ่มชำระเงินออนไลน์เมื่อมีความพร้อมด้านผู้ให้บริการ การคืนเงิน และการจัดการข้อผิดพลาด

10. ขอบเขต MVP และเกณฑ์ทดสอบ

ฝั่งนักศึกษา

  • ดูร้านค้าและเมนู
  • เลือกอาหาร จำนวน และรายละเอียด
  • เลือกช่วงเวลารับที่ยังไม่เต็ม
  • ยืนยันออเดอร์และรับหมายเลขคิว
  • ดูสถานะออเดอร์
  • ยืนยันรับอาหารหรือแจ้งปัญหา

ฝั่งร้านค้า

  • เข้าสู่ระบบร้านค้า
  • แก้ไขเมนู ราคา และเวลาทำโดยประมาณ
  • เปิดหรือปิดรับออเดอร์
  • ดูและยืนยันออเดอร์ใหม่
  • เปลี่ยนสถานะกำลังทำและพร้อมรับ
  • ยืนยันส่งมอบอาหาร

ระบบกลาง

  • บันทึกออเดอร์ลงฐานข้อมูล
  • ป้องกันการจองเกินความจุ
  • ซิงก์สถานะให้ทั้งสองฝั่ง
  • บันทึกเวลาสั่ง รับงาน พร้อมรับ และรับอาหาร
  • มีหน้าผู้ดูแลตรวจสอบเหตุการณ์ผิดปกติ

เกณฑ์ทดสอบขั้นต่ำ

  • ออเดอร์ที่ยืนยันแล้วปรากฏในหน้าร้านค้า
  • การเปลี่ยนสถานะฝั่งร้านสะท้อนฝั่งนักศึกษา
  • ไม่สามารถจองเกินความจุของช่วงเวลาได้ แม้กดยืนยันพร้อมกัน
  • ร้านปิดรับแล้ว ผู้ใช้ไม่สามารถจองรอบที่ปิดได้
  • ออเดอร์ล่าช้าหรือยกเลิกมีสถานะที่ชัดเจน
  • ผู้ใช้ทดสอบทำภารกิจหลักสำเร็จโดยไม่ต้องมีคนอธิบายทุกขั้นตอน

11. ตัวชี้วัดความสำเร็จ

ควรเก็บค่าฐานก่อนใช้ระบบ แล้วเปรียบเทียบกับช่วงทดลองใช้ โดยพยายามเลือกช่วงเวลาที่ใกล้เคียงกันและบันทึกปัจจัยที่อาจมีผล

  • เวลารออาหาร: นาทีตั้งแต่เข้าคิวหรือสั่งจนได้รับอาหาร
  • ความตรงต่อเวลา: สัดส่วนออเดอร์ที่พร้อมในช่วงที่แจ้ง
  • ความแออัด: จำนวนคนรอในบริเวณที่กำหนด ณ เวลาที่สังเกต
  • ออเดอร์ไม่มารับ: จำนวนและสัดส่วนออเดอร์ที่ไม่ถูกรับ
  • ภาระงานร้านค้า: เวลาและขั้นตอนที่ใช้จัดการออเดอร์
  • Usability: อัตราทำภารกิจสำเร็จ เวลาในการทำ และข้อผิดพลาด

ไม่ควรกำหนดเป้าลดเวลารอเป็นเปอร์เซ็นต์สูง ๆ โดยไม่มีข้อมูลรองรับ ให้เก็บค่าฐานและกำหนดเป้าหมายหลังสำรวจ

12. เทคโนโลยีและสถาปัตยกรรม

Stack ที่เป็นไปได้

  • UX/UI: Figma
  • Frontend: React หรือ Next.js
  • Backend และฐานข้อมูล: Supabase / PostgreSQL
  • Hosting: Vercel หรือบริการที่ทีมดูแลได้
  • Notifications: เริ่มจากสถานะในเว็บ แล้วเพิ่ม Web Push เมื่อจำเป็น

ส่วนประกอบระบบ

  • Student Web App: ร้านค้า เมนู การสั่ง รอบเวลารับ และติดตามสถานะ
  • Merchant Web App: เมนู ออเดอร์ สถานะ และการหยุดรับคิว
  • Backend/API: ตรวจสอบสิทธิ์ จองความจุ เปลี่ยนสถานะ และตรวจสอบความถูกต้อง
  • Database: ผู้ใช้ ร้านค้า เมนู รอบเวลา ออเดอร์ และประวัติสถานะ

ความปลอดภัยและข้อมูล

  • เก็บข้อมูลส่วนบุคคลเท่าที่จำเป็น
  • จำกัดสิทธิ์ให้ร้านเห็นเฉพาะออเดอร์ที่เกี่ยวข้อง
  • ตรวจสอบการจองและการเปลี่ยนสถานะฝั่งเซิร์ฟเวอร์
  • กำหนดระยะเวลาเก็บข้อมูลและแนวทางลบข้อมูล
  • ไม่แสดงข้อมูลส่วนบุคคลของนักศึกษาต่อสาธารณะ

เทคโนโลยีที่เลือกเป็นตัวอย่าง ไม่ใช่ข้อบังคับ ควรพิจารณาทักษะของทีม งบประมาณ และเงื่อนไขการใช้งานของบริการแต่ละราย

13. ความเสี่ยงและแนวทางรับมือ

  • ร้านไม่อยากใช้: ทดลองกับร้านที่สมัครใจ ใช้อุปกรณ์เดิม และลดจำนวนขั้นตอน
  • ออเดอร์ออนไลน์แย่งคิวหน้าร้าน: กันกำลังการผลิตสำหรับหน้าร้านและให้ร้านปรับความจุได้
  • เวลารับไม่แม่น: ใช้เวลาโดยประมาณและให้ร้านแจ้งล่าช้า
  • ลูกค้าไม่มารับ: กำหนดเวลารับและนโยบายยกเลิก
  • แจ้งเตือนไม่ถึง: มีหน้าติดตามสถานะและหมายเลขออเดอร์
  • ไม่ลดความแออัด: วัดจำนวนคนก่อน–หลังและทบทวนตำแหน่งจุดรับ
  • ข้อมูลรั่วไหล: จำกัดสิทธิ์เข้าถึงและเก็บข้อมูลเท่าที่จำเป็น

การลดคิวอาหารไม่ได้เพิ่มที่นั่งในโรงอาหาร หากปัญหาหลักคือที่นั่งไม่พอ ต้องแยกเป็นโจทย์อีกส่วนหนึ่ง

14. แผนดำเนินงาน 8 สัปดาห์

  1. สัปดาห์ 1 — User Research: สัมภาษณ์ สังเกต และเก็บเวลารอ
  2. สัปดาห์ 2 — Define & Scope: สรุปปัญหา Persona, Journey Map และ MVP
  3. สัปดาห์ 3 — UX/UI: ออกแบบ User Flow, Wireframe และ Design System
  4. สัปดาห์ 4 — Prototype Testing: ทดสอบต้นแบบและปรับปรุง
  5. สัปดาห์ 5–6 — Development: พัฒนาหน้าผู้ใช้ หน้าร้าน ฐานข้อมูล และกติกาจัดคิว
  6. สัปดาห์ 7 — Integration & QA: ทดสอบการจองพร้อมกัน สถานะผิดพลาด และความล่าช้า
  7. สัปดาห์ 8 — Pilot & Evaluation: ทดลองกับร้านที่เข้าร่วมและวัดผล

แผนนี้เป็นประมาณการสำหรับทีมที่มีเวลาทำงานต่อเนื่อง หากไม่มีประสบการณ์พัฒนา Backend อาจต้องเพิ่มเวลา หรือลดขอบเขตให้เล็กลง

15. สิ่งที่ควรทำต่อทันที

  1. ลงพื้นที่โรงอาหารท่าพระจันทร์และสังเกตช่วงเร่งด่วน
  2. สัมภาษณ์นักศึกษาและร้านค้าโดยไม่ชี้นำคำตอบ
  3. สรุปปัญหาที่พบจริงและจัดอันดับความสำคัญ
  4. เลือก 3–5 ร้านที่สนใจเข้าร่วมทดลอง
  5. สร้าง User Flow และ Wireframe ก่อนพัฒนา
  6. ทดสอบต้นแบบกับผู้ใช้ทั้งสองกลุ่ม
  7. พัฒนา MVP และทดลองแบบจำกัดขอบเขต
  8. เปรียบเทียบข้อมูลก่อนและหลังใช้งาน
ข้อเสนอแนะสุดท้าย: เริ่มจากสั่งอาหารล่วงหน้า + กระจายเวลารับ + หน้าจัดการออเดอร์ร้านค้า ให้ทำงานร่วมกันได้ก่อน แล้วค่อยเพิ่มการชำระเงินออนไลน์ การวิเคราะห์ความหนาแน่น หรือการจองที่นั่งเมื่อมีหลักฐานว่าจำเป็น
